# 结对过程记录

> 本次作业由同学A与同学B结对完成。
> 📷 **本文档中的「截图占位」需要替换为你们讨论时的真实照片或截图**，建议拍摄：两人讨论需求、画流程图、一起看原型屏幕的场景。

## 一、分工方式

| 同学 | 主要职责 | 具体工作 |
| --- | --- | --- |
| **同学A**（本人） | 负责**基础功能** | 需求整理、流程图绘制、7 个原型页面的制作、作业文档撰写 |
| **同学B**（队友） | 负责**优化功能** | 需求补充访谈、视觉规范建议、原型评审、博客框架与截图整理 |

结对并不意味着"各做一半然后拼起来"。我们的做法是：**关键决策必须两人一起讨论后确定**，确定之后再分头执行，执行结果再由对方评审。

## 二、结对过程记录

### 第 1 次讨论（09-21，约 25 分钟）：拆解问题

**目标**：搞清楚"到底要解决什么问题"。

我们先把客户描述读了两遍，各自在白纸上写下"我觉得最难受的一点"，然后对照：

- 同学A 写下的是：**信息容易被群消息淹没**。
- 同学B 写下的是：**发在班级群里的信息，别的班的人看不到**。

两个答案其实指向同一个根源，但角度不同：一个是"时间维度"上的失效（信息会过期），一个是"空间维度"上的失效（信息传不出去）。我们把这两点合并成了需求分析里的"容易被淹没"和"供需不对称"，并由此得出一个关键结论：

> **这个产品真正要解决的问题，不是"聊天"，而是"让信息被找到"。**

这个结论直接决定了后面所有的设计——不做站内聊天，而是把力气放在**分类**和**搜索**上。

> 📷 *截图占位：两人讨论需求时在白纸上写的要点*

### 第 2 次讨论（09-22，约 45 分钟）：确定功能与页面

**目标**：把需求翻译成功能清单和页面。

我们先按"用户打开小程序后会做什么"排了一遍动作顺序，得到三个动作：**看、发、找**。对应到页面就是：首页（看）、发布页（发）、搜索页（找），再加上看具体某条信息的详情页。

讨论中出现的分歧：

| 分歧点 | 同学A 的意见 | 同学B 的意见 | 最终决定 |
| --- | --- | --- | --- |
| 联系发布者怎么做 | 做一个简单的站内留言 | 直接展示微信号，去微信加好友 | **采纳同学B**：站内留言需要对方也常来看，反而更慢；微信是大家本来就在用的工具 |
| 要不要做实名认证 | 不做，作业也没要求 | 至少显示学院，增加可信度 | **折中**：不做认证，但在详情页展示发布者的学院信息 |
| 首页卡片显示什么 | 只显示标题和地点 | 还要显示是谁发的 | **采纳同学B**：看到熟悉的名字会更容易建立信任 |

这一轮还确定了配色规范：**绿色代表"招领"，橙色代表"寻物"**。

> 📷 *截图占位：两人一起画页面草图 / 讨论功能清单*

### 第 3 次讨论（09-23，约 35 分钟）：评审原型

**目标**：检查原型是否能跑通作业要求的三条流程。

同学A 先演示了原型，同学B 拿着作业要求逐条对照，发现一个**问题**：

> 作业要求演示"搜索物品 → **查看搜索结果**"，但原型里搜完之后直接跳到了详情页，中间缺少"结果列表"这一环。如果搜"校园卡"直接跳到某一条详情，用户就没法从多条结果里挑。

于是补充了 **05 搜索结果页**，并加上"关键词高亮"的设计。同时把"发布成功"从一句 toast 升级为一个带引导按钮的弹层（**03 发布成功页**）。

这次评审也验证了流程的闭环：从首页出发，无论是"看→详情→联系"，还是"发→成功→我的发布"，还是"搜→结果→详情"，都能走通且能回到起点。

> 📷 *截图占位：评审时两人一起看原型屏幕的照片*

### 第 4 次讨论（09-25，约 40 分钟）：交叉检查

- 同学B 检查：作业要求的 6 个功能点是否都有对应页面 → 全部覆盖。
- 同学A 检查：每条流程是否闭环 → 通过。
- 两人分别撰写个人总结。

## 三、遇到的困难与解决

| 困难 | 解决方式 |
| --- | --- |
| 一开始分不清"需求"和"功能"，写出来的都是功能 | 用"用户故事"的句式（作为……我希望……这样……）重写一遍，需求就浮出来了 |
| 两位同学对"要不要做聊天"意见不一致 | 回到最初的问题定义——我们要解决的是"让信息被找到"而不是"聊天"，用目标来裁决分歧 |
| 原型页面之间的配色和卡片样式不统一 | 先抽出设计规范（主色、字号、圆角、卡片结构），再统一调整 |
| 不确定"原型要画多细" | 参照作业要求里"至少能演示三条基本流程"作为标准，能点通流程即可，不追求视觉细节 |

## 四、对第二次结对编程的准备

本次原型刻意保持了**功能简单、流程清楚**，就是为了让第二次结对编程容易落地：

1. 7 个页面中，4 个是作业要求的核心页面，3 个是流程演示页面，实现优先级清晰。
2. 功能清单已区分 🟢 基础功能（同学A）与 🔵 优化功能（同学B），可以直接作为编码阶段的任务拆分。
3. 数据结构已经隐含在原型里，可直接导出为数据表设计：

```
信息(Info)
├── id            信息编号
├── type          类型：寻物 / 招领
├── title         物品名称
├── category      物品分类
├── place         地点
├── happened_at   丢失/拾取时间
├── description   详细描述
├── contact       联系方式
├── status        状态：进行中 / 已解决
└── created_at    发布时间
```

4. 我们已按作业建议注册并熟悉了 GitHub，第二次结对编程将通过 GitHub 进行代码协作（一人 fork，另一人提 Pull Request，互相 Review 后合并）。
